1. 현재 구조 개요

스키마는 JPA 엔티티(com.example.triplesweb.entity)로 관리되며, 물리 네이밍은 PhysicalNamingStrategyStandardImpl을 사용해 클래스명·필드명이 테이블·컬럼에 거의 그대로 반영됩니다. (article_file, article_like, Chemistry 등 일부만 @Table로 명시)

게시판·회원

Members, Article, Comment, article_like, article_file

아티스트·유닛

Artist, Unit, UnitMember, Album, Track, Chemistry

쇼핑

Shop, ShopImage

미디어·일정

Media, Archive, Schedule (+ Media는 JSON 카탈로그와 병행)

2. 현재 ERD (As-Is)

각 박스 = 테이블. PK 기본키, FK 외래키, UK 유니크. 점선 관계는 DB FK 없이 문자열만 연결.

3. 테이블·컬럼·역할 상세 (As-Is)

3.1 Members — 사이트 회원

역할: 로그인·권한·레벨·포인트 보관. 현재 로그인/회원가입은 비활성(리다이렉트)이며 Repository도 없어 사실상 미사용.

userIdVARCHAR UK로그인 ID
passwordVARCHAR비밀번호

addressVARCHAR주소
roleVARCHAR권한 (기본 ROLE_USER)
levelINT레벨
pointsINT포인트

역할: 커뮤니티 게시글. Comment / article_like / article_file과 1:N. userId는 Members와 논리만 연결.
컬럼타입·제약설명

titleVARCHAR제목
contentLONGTEXT본문 HTML
categoryVARCHARfree/chat/notice/trade 등

formatted_created_atDATETIME작성 시각

3.3 Comment — 댓글

역할: 게시글 댓글. article_id → Article (FK).

3.4 article_like — 게시글 좋아요

역할: (게시글, 사용자) 단위 좋아요. UNIQUE(article_id, userid). Article.likesCount와 이중 관리.

article_idBIGINT FK게시글

역할: 멤버 프로필. UnitMember로 유닛 소속.

역할: Artist ↔ Unit M:N. (artist_Id, unit_id) UNIQUE 제약은 없음.

역할: 앨범(Unit N:1)과 수록곡(Album 1:N). 앨범 상세 트랙리스트에 사용.

역할: 멤버 페어별 케미명·설명·이미지. memberA/B는 한글 이름 문자열(Artist FK 없음). UK(memberA, memberB).

3.11 Shop / ShopImage

역할: 굿즈 상품과 이미지(1:N). 상세 페이지 슬라이드에 다장 사용.

3.12 Media — 유튜브 미디어

역할(의도): 탭별(mv/signal 등) 유튜브 카탈로그. 실제: MediaService는 JSON 파일만 사용. MediaRepository 호출 0회. 엔티티 PK(String)와 Repository 제네릭(Long) 불일치.
컬럼설명
id문자열 PK
tab, mediaTitle, mediaDur, youtubeId, viewCount, description탭·제목·길이·YT ID·조회수(문자열)·설명

3.13 Archive — 자료실

역할: 독립 업로드 자료. SavedMeta 임베드. article_file과 역할이 다름(자료실 vs 게시 첨부).

3.14 Schedule — 일정

역할: 캘린더 일정(제목·시작·종료일).

3.15 SavedMeta / MediaType (테이블 아님)

SavedMeta는 Embeddable(원본명·저장명·url·size·fileType·mediaType). MediaType은 IMAGE/VIDEO/OTHER enum.

4. 개선점

1) article_like → Article로 합치기
“누가 눌렀는지”보다 “몇 개”만 필요하면 별도 테이블이 과함. 현재도 좋아요가 anonymous 고정. 제거 Article.likesCount만 유지. (1인 1좋아요·유저별 목록이 필요해지면 조인 테이블 복구)
2) Members 제거 (또는 회원 복구 시 FK 연결)
로그인 미사용·Repo 없음. 유지할 가치 낮음. 제거 회원 기능을 살릴 경우 Article/Comment에 members.id FK를 추가.
3) Media는 JSON 대신 DB 유지·정비
탭 페이징·youtubeId 중복·다중 인스턴스·백업 측면에서 DB가 유리. JSON 카탈로그를 버리고 JPA로 이전. 유지·강화 PK를 surrogate id + youtubeId UNIQUE, viewCount를 BIGINT로.
4) Chemistry → Artist FK
memberA/B 문자열·서비스 하드코딩 멤버 리스트 제거. artist_a_id, artist_b_id + UNIQUE(pair). 관계 추가
5) 중복·타입 정리
article_file.category 제거 · 날짜 VARCHAR→DATE · PK 네이밍 통일(id) · UnitMember (artist_id, unit_id) UNIQUE · 테이블명 snake_case 통일 권장.
합치지 않는 것
Comment, article_file, Track, ShopImage, Archive vs Media(유튜브) — 생명주기·카디널리티·도메인이 달라 분리 유지.

6. 개선 ERD 설명

6.1 게시판 영역

게시글(Article)이 중심이며 댓글·첨부만 1:N으로 연결합니다. 좋아요는 카운터 컬럼만 두어 쓰기/조회가 단순해집니다. 작성자 userId는 표시용이며, 회원 테이블이 없으므로 FK는 두지 않습니다.

6.2 아티스트·유닛·앨범

Artist–Unit은 unit_member로 M:N, Unit은 상위·하위 자기참조, Unit–Album–Track은 발매·수록 계층을 그대로 유지합니다. Chemistry만 Artist에 FK로 묶어 이름 변경·하드코딩 문제를 제거합니다.

6.3 쇼핑·자료·일정·미디어

  • Shop–ShopImage: 다장 갤러리용 1:N 유지
  • Archive: 독립 자료실 (게시 첨부와 분리)
  • Schedule: 독립 일정
  • Media: 유튜브 카탈로그의 단일 소스. JSON 파일 저장을 폐기하고 DB만 사용
